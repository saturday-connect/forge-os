# Forge OS - Developer Reference

> Version: 0.2.0. Python 3 stdlib runtime. Root orchestrator plus generated project runtimes.

## Product Overview

Forge OS is a documentation-first PDLC and build orchestration framework. It treats Markdown files and generated runtime state as the control plane for product planning, generation, review, build, and deployment.

The original concept was a library used inside one project. The current direction is different: Forge stands at the repository root as a top-level orchestrator and manages multiple generated projects under `.projects/`.

Current lifecycle:

```text
Projects -> Input -> Generate -> Review -> Build -> Deploy
```

The dashboard is now project-first. A user starts at the Projects page, creates or selects a project, then operates the lifecycle for that project.

## Architecture: Current Source Layout

The old documentation described a single god script. That is no longer the maintainable source model.

Current model:

```text
src/build_forge.py                 compiler and compatibility assembly
src/runtime/forge_cli.py.tmpl      CLI template compiled into ./forge
src/runtime/server.py              dashboard API server copied to .forge/scripts/server.py
src/runtime/build_runner.py        build-system runner copied to .forge/scripts/build_runner.py
src/dashboard/index.html           dashboard HTML shell
src/dashboard/styles.css           dashboard CSS source
src/dashboard/scripts/*.js         dashboard JS source, assembled in order
src/dashboard/scripts.txt          dashboard script assembly order
src/dashboard/DESIGN.md            active dashboard design contract
src/dashboard.html                 generated compatibility snapshot
forge                              built executable artifact
```

Important rules:

- Do not hand-edit `src/dashboard.html` as source. It is generated from `src/dashboard/*`.
- Do not hand-edit `.forge/scripts/*` as source. It is generated by `./forge upgrade`.
- Edit `src/runtime/*`, `src/dashboard/*`, or `src/build_forge.py`.
- Rebuild with `python3 src/build_forge.py` after source changes.
- Upgrade root and target projects after rebuilding.

## Build And Deploy Cycle

```bash
python3 src/build_forge.py
./forge upgrade
./forge --project "$PWD/.projects/task-flow" upgrade
./forge --project "$PWD/test-projects/saas-todo" upgrade
```

Restart dashboard:

```bash
screen -S forge-dashboard -X quit >/dev/null 2>&1 || true
lsof -tiTCP:8080 -sTCP:LISTEN | xargs -r kill
screen -dmS forge-dashboard ./forge dashboard 8080
curl -sS -o /tmp/forge-dashboard.html -w '%{http_code} %{size_download}\n' http://127.0.0.1:8080/
```

Expected successful response:

```text
200 <non-zero-size>
```

## CLI Reference

Current command surface:

| Command | Description |
|---|---|
| `./forge version` | Print Forge version. |
| `./forge init` | Initialize `.forge/` in the current project. |
| `./forge --project <path> init` | Initialize a specific project. |
| `./forge upgrade` | Update generated runtime files while preserving state. |
| `./forge generate <stage>` | Generate one stage. |
| `./forge pipeline` | Run all documentation stages. |
| `./forge dashboard [port]` | Start dashboard server. |
| `./forge dev [port]` | Build, init, symlink dashboard snapshot, and serve. |

Notes:

- `--project <path>` goes before the command.
- `./forge` with no command prints usage.
- `./forge --help` is not the primary help command.

## Managed Project Model

Managed projects are created under `.projects/<slug>` and tracked in `.projects/index.json`.

Project lifecycle:

- Create project from dashboard Projects page.
- Select/open project.
- Archive project before deletion.
- Restore archived project when needed.
- Permanently delete only archived projects.

Project APIs:

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/projects` | List active and archived projects. |
| `POST` | `/api/projects` | Create a project under `.projects/<slug>`. |
| `POST` | `/api/projects/select` | Set active project. |
| `POST` | `/api/projects/archive` | Archive active project. |
| `POST` | `/api/projects/restore` | Restore archived project. |
| `DELETE` | `/api/projects` | Permanently delete archived project. |

Operational decisions:

- `.projects/` is gitignored.
- Project directories still contain `.git` when the build workflow needs git behavior internally.
- Archive is the default safe removal path; delete is intentionally separated.

## Dashboard Design State

Final active design direction is Revolut-inspired.

Design source:

- `src/dashboard/DESIGN.md`
- `src/dashboard/styles.css`

Current design rules:

- True black project/root entry surface.
- White operational dashboard surfaces.
- Cobalt violet `#494fdf` as scarce accent.
- Pill buttons and tabs.
- 20px cards.
- 12px inputs.
- Aeonik-style display fallback stack.
- No traditional card shadows as the main depth language.

Important adaptation rule:

- Marketing design documents cannot be applied literally to a dense dashboard. Preserve design intent, but protect readability, accessible hit areas, control density, and overflow behavior.

## State Files

Important state files:

```text
.forge/project-state.json
.forge/reviews.json
.forge/runs/status.json
.forge/runs/build-system.json
.forge/runs/build-review.json
.projects/index.json
```

`project-state.json` persists project settings, git config, environment config, build history, issues, and configured-secret metadata.

Security rule:

- Treat `project-state.json` as sensitive. It may contain tokens or operational details from earlier testing.

## Phase Computation

Lifecycle phase is computed from file/build state, not stored as the source of truth.

| Phase | Condition |
|---|---|
| `input` | No raw input files or all stage files are empty. |
| `generate` | Raw inputs exist but generated docs are below threshold. |
| `review` | Generated docs exist but not all are reviewed. |
| `build` | Generated docs are reviewed and no build exists. |
| `deploy` | At least one build exists. |

## Gate System

Gate files live in `.forge/12-gates/<gate>.md`.

Review status lives in `.forge/reviews.json`.

A gate passes only when every generated non-empty file mapped to that gate is reviewed.

Known gate mapping:

```text
context-gate      -> 00-context
prd-gate          -> 01-requirements
design-gate       -> 02-design
architecture-gate -> 04-architecture
engineering-gate  -> 06-engineering
qa-gate           -> 07-quality
release-gate      -> 09-release
marketing-gate    -> 10-marketing
```

## Build System

Build artifacts are generated under `.forge/15-build/*` and may be copied into project directories such as:

- `backend`
- `frontend`
- `integration`
- `tests`
- `infra`

Build-system status lives in:

```text
.forge/runs/build-system.json
```

Pre-push review status lives in:

```text
.forge/runs/build-review.json
```

Secrets flow:

- Required secrets are parsed from generated `secrets-required.md` files.
- `GET /api/secrets` reports required/configured status.
- `POST /api/secrets` pushes via GitHub CLI when available or GitHub API when supported.
- Do not store plaintext secret values in docs or commits.

## Failure Log And Lessons

### Stale generated dashboard

Symptom:

- Browser showed old UI after source changes.

Cause:

- Source fragments changed but `src/dashboard.html` and `.forge/scripts/dashboard.html` were not regenerated/upgraded.

Fix:

- Rebuild with `python3 src/build_forge.py`, then run `./forge upgrade` and project upgrades.

### Server not reachable

Symptom:

- Browser showed site cannot be reached.

Cause:

- Server process was not running, wrong project target was used, or port 8080 had stale state.

Fix:

- Kill the old screen/port listener, restart with `screen -dmS forge-dashboard ./forge dashboard 8080`, verify with `curl`.

### Blank browser page after design experiment

Symptom:

- HTTP returned 200 but browser rendered a blank/loading page.

Cause:

- A design experiment introduced unstable generated output and browser tab state was stale/hung.

Fix:

- Revert to known-good design source, rebuild, upgrade, restart, and open a fresh tab.

### Review side-panel overflow

Symptom:

- `Regenerate with critique` clipped in the Review panel.

Cause:

- Fixed side panel width plus global nowrap button styling.

Fix:

- Widen Review panel, constrain button typography, ellipsize filenames/metadata, and rerun UI sanity scan.

### Marketing design over-application

Symptom:

- A pasted onboarding/marketing design MD produced poor dashboard usability.

Cause:

- Marketing design systems often assume sparse landing-page content, not dense dashboard controls.

Fix:

- Apply design intent through tokens and component rules, but adapt layout for dashboard readability and interaction density.

### Git worktree config compatibility

Symptom:

- Commit tooling error: `core.repositoryformatversion does not support extension: worktreeconfig`.

Takeaway:

- Codex worktrees may expose Git config compatibility issues. Only disable worktreeConfig if per-worktree config is not needed.

## Security And Hygiene

Rules:

- Do not commit `.projects/` runtime state.
- Do not expose `.forge/project-state.json` without checking for secrets.
- Do not paste tokens, repo credentials, AI keys, or environment values into docs, logs, or chat.
- Generated build artifacts may include `.env.example` and secret requirement docs; review before sharing.
- Store configured-secret status as metadata, not plaintext secret values.
